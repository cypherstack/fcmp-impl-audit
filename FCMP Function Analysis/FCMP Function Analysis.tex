\section{Structure}
\indent \indent This document is structured with each section addressing a particular point in the audit request. Every section is structured similarly: we begin with a mathematical overview of the purpose of the code covered in each section, proceed with an analysis of all pertinent functions, then end with a section that addresses the questions included in the audit request.

Each instance of a function's analysis is structured identically: 
\begin{enumerate}
    \item \textbf{Functionality}: This segment presents the code for the analyzed functions as written in the repository, along with a Source-to-Specification map detailing the operations contained within the function. Additionally, it includes where the code can be found in the repository.
    
    \item \textbf{Implementation Observations}: In this component, we include our observations surrounding the code, how it implements the underlying mathematical concepts, and any potential issues that may arise from a disconnect between the code and the math.
    
    \item \textbf{Edge Case Analysis}: Here, we deal with determining how the code handles extreme, rare, or impossible inputs. The purpose is mainly to determine if there are fringe cases which the function cannot handle, but additionally this analysis provides insight into potential guardrails that may need to be placed on the function.
    % put in place if the functions are used in a context outside of its primary use.
    
    \item \textbf{Fuzzing Results}: Fuzzing is a compilation of results wherein the function is executed on a variety of platforms and infrastructure over a wide range of inputs, with the goal of determining if there are any purely code-based concerns to be addressed.
    
    \item \textbf{Conclusion}: Finally, the section conclusion will be a short determination of our professional opinions regarding if the code is fit for deployment or not. For ease of reading, a green checkmark $\checkmark$, yellow checkmark $\checkmarky$, or red x \redx \,  will be included to indicate, respectively: yes, yes with minor concerns, or no.
\end{enumerate}

If there are any additional results, we include them in a dedicated section with the relevant function. Additionally, if there is no edge case analysis section, then it should be interpreted that all relevant behavior is captured in the fuzzing results or that there were no notable interactions.

\medskip
As a convention, when code is being discussed, the first two columns we label L1 and L2. Firstly, L1 is the line location in the source code, while L2 is the code's line location in the document.

\section{Constant Time}

\indent \indent We note that constant-timedness is critical for the implementation of various functions utilized in FCMP++. The purpose is to ensure that timing information is not leaked during the execution of the function: as all computations run using the same amount of time regardless of input, timing analysis loses its utility. These considerations are only necessary in the case that the function inputs are private; indeed if all the information needed to initialize the function is public, then no advantage can be gained from a timing attack, so constant time is not necessary. With this in mind, the function is free to default to whichever method results in the fastest runtime.

\subsection{Mathematical Overview}
\begin{df}{Pedersen Commitments}{PC}
A \textbf{Pedersen commitment} $C$ to an amount $a$ with blinding factor $r$ is defined as:
$$C = r \cdot G + a \cdot H$$
where $G,H$ are both elliptic curve points such that the discrete logarithm relationship between them is unknown and presumed to be difficult to determine.

\medskip
A \textbf{zero commitment} to an amount $a$ is defined as a Pedersen Commitment with a blinding factor equal to $1$:
$$C_{zero} = 1 \cdot G + a \cdot H$$
\end{df}

For the purpose of this PR, $G$ is the base point for ED25519 and $H$ is Monero's second generator, which is a hash of $G$.

\medskip
\begin{df}{Binary Decomposition}{BD}
Any 64 bit unsigned integer $a$ can be uniquely represented as:
$$a = \sum_{k =0}^{63} a_k \cdot 2^k$$
where $a_k \in \{0,1\}$.
\end{df}

\medskip
There are a number of different point representations that are used in the code, which are used for the sake of efficiency. In general, a point $(x,y)$ on a \textit{Twisted Edwards Curve} given by $-x^2 + y^2 = 1 + dx^2y^2$ can be represented in the following ways. For ED25519, the curve parameter is the constant $d = -\frac{121665}{121666} \pmod p$, where $p = 2^{255} - 19$.

\section{Batch Inverse}
\subsection{Mathematical Overview}
\indent \indent The following code performs the Montgomery trick for group inversion. Instead of inverting $n$ group elements individually, it batches them together and inverts once, which still results in the inversions of each of the elements, but requires $1$ inversion and $3(n-1)$ group multiplications as opposed to $n$ costly inversions.

\medskip
The trick works as follows: let $a_1,...,a_n$ be the group elements one wishes to invert. Perform the following:
\begin{enumerate}
\item For each $1 \leq i \leq n$, compute the product:
$$P_i = \prod_{k = 1}^i a_k$$
\item Invert the product of all the elements:
$$I_n = P_n^{-1}$$
\item For each $1 \leq i \leq n$, compute the following:
$$I_{i - 1} \equiv I_i \cdot a_i \, \, \, (mod \, \, \, p)$$
$$a_i^{-1} \equiv P_{i - 1} \cdot I_i \, \, \, (mod \, \, \, p)$$
\end{enumerate} 

\medskip
We can see that, since there are $n$ elements, Line 1 requires $n-1$ multiplications (since $P_1 = a_1$). Line 2 is the expensive operation, requiring $1$ inversion. For the first part of Line 3, we require $n-1$ multiplications, since it terminates for $i = 2$. Similarly, we require $n - 1$ multiplications for the second part, bringing the total operation count to $3(n-1)$ multiplications and $1$ inversion.

\subsubsection{Implementation Observations}
\begin{enumerate}
\item \verb|out[]| is dual-use: the forward pass stores the prefix products in \verb|out[i]|, the backward pass reads \verb|out[i-2]| and overwrites \verb|out[i-1]|. This is done so that none of the prefix products are consumed after an overwrite.

The inversion step returns zero after leveraging Fermat's Little Theorem, in essence sterilizing the output results. To prevent this fruit from the poisonous tree, non-zero inputs must be guaranteed when called.

Since a negative value for $n$ still passes the \verb|n == 0| check, the function proceeds to \verb|fe_invert(a, out[n-1])| with a negative index, reading out of bounds: this is the actual source of undefined behavior, not the (then-skipped) loops.  Practically, this will never happen, but it should be noted regardless.
\item The overlap assertion is debug-only, so release builds will have no aliasing protect. Aliasing corrupts output silently. \\
\item There is a potential bug in the header docstring. The document comment says \\
 \verb|@return: 0 on success|, but the function signature is void. No return value exists.
\end{enumerate}

\section{ED25519 to X25519 Point Conversion}
The purpose of this section will be to determine the following:
\begin{enumerate}
    \item From a cryptographic standpoint, do the functions properly derive the X25519 $x$-coordinate from an ED25519 point?
    \item Is the code in each function implemented correctly assuming the above is true?
\end{enumerate}

\subsection{Mathematical Overview}
Ed25519, in its Twisted Edwards form, is defined as
$$-x^2 + y^2 =  1 + dx^2y^2 \, \, \, over \, \, \, \mathbb{F}_p$$
where $p = 2^{255}-19$ and $d = -\frac{121665}{121666}$.

\medskip
Curve25519, in its Montgomery form, is given as the polynomial:
$$v^2 = u^3 + 486662u^2 + u \, \, \, \text{over} \, \, \, \mathbb{F}_p$$

\medskip
It is known that these two curves are \textit{birationally equivalent}, which loosely means that, with the exception of a small subset of points, the curves are isomorphic to each other. So given a point $(x,y)$ on the first curve, one can determine the corresponding coordinate on the second curve using the map
$$u = \frac{1+y}{1-y},$$
which is valid for all values except $y = 1$ (the Edwards identity, where the denominator vanishes).

\medskip
The following functions are used to compute this conversion.

The goals of this section are to answer the following questions:
\begin{enumerate}
\item Does each function, when called, soundly perform as desired in a cryptographic sense?
\item Is the code in each function implemented correctly?

\end{enumerate}

The focus of the first three subsections will be looking at the code as it is written and ensuring that each of the functions does what it is intended to do.
\subsection{Mathematical Overview}
When dealing with a non-prime order group, it is not guaranteed that a randomly chosen point will fall in a prime order subgroup. In this particular instance, the ED25519 curve has order
$|\mathbb{E}(\mathbb{F}_p)| = 8 \ell$
where $\ell = 2^{252} + 27742317777372353535851937790883648493
$, which is prime. The purpose of torsion clearing is to make sure that values do not inadvertently fall into the subgroup of order 8, as many of the security properties that ED25519 enjoys are not valid in the smaller subgroups.
% the chosen point is not in the larger subgroup of order $\ell$.

\medskip
In order to be explicit, the torsion subgroup of ED25519, which we will call $\mathbb{E}_8$, we represent as 
$\mathbb{E}_8 = \{\mathcal{O},T_1,...T_7\}.$
Each of the points are defined as follows:
\begin{table}[htbp]
\centering
{\rowcolors{2}{SeaGreen!5}{SeaGreen!25}
\begin{tabular}{| l | c | l|}
\hline
\textbf{Point} & \textbf{Coordinates} & \textbf{Order} \\
\hline
\hline
$\mathbb{O}$ & $(0,1)$ & $1$ \\
$T_1$ & $(0,-1)$ & $2$ \\
$T_2$ & $(1,0)$ & $4$ \\
$T_3$ & $(-1,0) $ & $4$\\
$T_4$ & $(\rho, \gamma)$ & $8$ \\
$T_5$ & $(-\rho, \gamma)$& $8$\\
$T_6$ & $(\rho, -\gamma)$& $8$\\
$T_7$ & $(-\rho, -\gamma)$& $8$\\
\hline
\end{tabular}}
\end{table}
\newpage
where
$$\rho = 2^{\frac{p - 1}{4}} \text{ mod } p \ \ \text{ and } \ \ \gamma = \left(\frac{1 + \rho}{2}\right)^{\frac{1}{2}} \text{ mod } p.$$

\medskip
In order to ensure points are not in $\mathbb{E}_8$, the following functions are used:
\begin{enumerate}
\item \verb+mul8_is_identity(P)+
\begin{itemize}
\item Computes $8 \cdot P$.
\item Checks if $8 \cdot P=0$
\end{itemize}
\item \verb+clear_torsion(P)+
\begin{itemize}
\item Given $P = P_0 + T$, computes $P_0$.
\item The above form is the decomposition of $P$ into an element of the prime order subgroup and the torsion subgroup.
\end{itemize}
\item \verb+get_valid_cleared_torsion_point(P,out)+
\end{enumerate}

The first function \verb+mult8_is_identity+ acts exactly how one would expect: it computes $8 \cdot P$ for  input point $P$, then determines whether the point is the identity or not. It does so via 3 point doublings, by computing $2 \cdot P \rightarrow 2 \cdot (2 \cdot P) = 4 \cdot P \rightarrow 2 \cdot (4 \cdot P) = 8 \cdot P$. It checks whether or not the output is the identity element as follows:
\begin{enumerate}
    \item The computed coordinates are converted to extended coordinates $(X:Y:Z:T)$.
    \item Determine if the point is equal to $(0:c:c:0)$, for some non-zero scalar $c$.
    \item If so, then the point is the identity element, otherwise it is not.
\end{enumerate}

\medskip
The second function \verb+clear_torsion+ is slightly more mathematically involved. Since the curve is a finitely generated group $G$, we can directly apply the \textit{fundamental theorem of finite abelian groups} to see that $G$ is isomorphic to the direct sum of cyclic subgroups of prime power order.

\medskip
Since $\mathbb{E}(\mathbb{F}_p) = 8 \ell$, this curve will be isomorphic to: $$\mathbb{Z}/8\mathbb{Z} \oplus \mathbb{Z}/ \ell \mathbb{Z}$$
This implies that every point $P$ on the curve can be expressed as the sum of two points $P_0$ and $T$, where:
$$P = P_0 + T$$
where $P_0$ is an element of order $\ell$ and $T$ is an element of order dividing $8$.

\medskip
In order to retrieve the $P_0$ point, we can perform the following procedure:
\begin{enumerate}
    \item Compute $8 \cdot P$. Simplifying the computation, we have:
    $$8 \cdot P = 8 \cdot (P_0 + T) = 8 \cdot P_0 + 8 \cdot T$$
    \item Since $T$ has an order dividing $8$, we have that:
    $$8 \cdot T = 0  \ \ \Rightarrow \ \ 8 \cdot P = 8 \cdot P_0$$
    \item Since $P_0$ has order $\ell$, it's a fact that $8 \cdot P_0$ remains in the prime subgroup. As such, $8^{-1}$ exists modulo $\ell$. So, we multiply by the inverse, resulting in
    $$8^{-1} \cdot (8 \cdot P) = P_0,$$
\end{enumerate}
where all operations take place in the appropriate modulus. Subsequently, the element produced is guaranteed to be an element of the prime order subgroup exclusively.

\medskip
The last function simply puts these two pieces together.

\section{ED25519 to Weierstrass Point Conversion}
The purpose of this section is as follows:
\begin{enumerate}
    \item Do the functions correctly implement the specification detailed in section E.2 of the paper linked: \\ {\small{\url{https://www.ietf.org/archive/id/draft-ietf-lwig-curve-representations-02.pdf}}}?
    \item Do the constants introduced (\verb+fe_a+, \verb+fe_a_inv_3+, \verb+fe_c+) match the constants specified in the paper?
    \item Is \verb+fe_ed_derivatives_to_wei_x_y+ constant time?
\end{enumerate}

\subsection{Mathematical Overview}
The following functions are used to convert elliptic curve coordinates from ED25519 in the Twisted Edwards form to short Weierstrass form, which is used in the FCMP++ tree construction. Since both the Selene and Helios curves are in short Weierstrass form, every output public key must be converted before it can be used as a leaf in the curve tree.

\medskip
In order to facilitate this, we convert first from Twisted Edwards coordinates to Montgomery coordinates, then from Montgomery to short Weierstrass form. The first conversion is done in the usual way (as detailed in PR \#9828), by setting:
$$u = \frac{1 + y}{1 - y} \, \, \, \, \text{ and } \, \, \, \, v =\frac{1+y}{(1-y) \cdot x}$$
The second conversion is also done in the usual way:
$$w_x = u + \frac{A}{3} \, \, \, \, \text{ and } \, \, \, \, w_y = c \cdot v$$
where the constants $A$, $\frac{A}{3} \ (\text{mod } p)$, and $c$ are hardcoded constants, defined in \verb+crypto-ops-data.c+ as:
\begin{itemize}
    \item The $A$ coefficient: \verb+fe_a+ $=486662$.
    \item The $\frac{A}{3} \text{ mod } p$ component: \verb+fe_a_inv_3+ (Stored as a 10-limb radix field element).
    \item The $c$ coefficient: \verb+fe_c+ $= \sqrt{-(A+2)} \mod p$,
\end{itemize}
where $p = 2^{255}-19$.

\subsubsection{Proof of Unbiasedness}
\indent \indent Let us assume first that Elligator 2 outputs only points with a square $x$-coordinate, which is only half of the points on the elliptic curve. The proposed solution by Kayaba was to invoke twice and sum the outputs to remove any bias. Here, we will confirm that this is the case.

\medskip
First, we show that a sum of squares can represent any point on the curve, so let $E$ be an elliptic curve of prime order $p$. Formally, we will show that for all $c \in \mathbb{F}_p$, we can find $a,b$ such that:
$$a^2 + b^2 \equiv c \text{ mod } p$$
Let $S$ be the set of squares in $\mathbb{F}_p$. If we include $0$, then by Euler's criterion:
$$|S| = \frac{p+1}{2}$$
Select an arbitrary $c$ and define the set difference as $S_c = \{c - s \mid s \in S\}$. Since this is simply a translation, the cardinality is invariant; hence, it must be that $|S| = |S_c|$. We then note that:
$$|S| + |S_c| = p + 1 > p = |\mathbb{F}_p|$$
As such, the intersection of $S$ and $S_c$ is non-empty. Since we've established the existence of an $x \in S \cap S_c$, it must be both a square, and $c$ minus a square: that is, there exist $a \in S$ and $b \in S_c$ such that
$$x = a^2 \, \, \, \text{ and } \, \, \, x = c - b^2.$$
Hence, $a^2 + b^2 = c$.

\medskip
Now we verify uniformity. We have shown that summing these coordinates can range the whole space, but it could be that certain points are much more likely outcomes than others, so we must establish that sums of this type are distributed uniformly. To show this, we count the number of solutions to $a^2 + b^2 \equiv c \text{ mod } p$. 

Let $p > 2$. Let $\chi$ be the Legendre symbol, defined as follows:
$$\chi(x) = \begin{cases}
    0 & \text{ if } x = 0, \\
    1 & \text{ if } x \text{ is a quadratic residue}, \\
    -1 & \text{ if } x \text{ is a non-residue}.
\end{cases}$$

For any $y \in \mathbb{F}_p$, the number of solutions to the equation $x^2 \equiv y \text{ mod } p$ is exactly $1+\chi(y)$. This can be readily seen by counting cases: if $y = 0$, there is only one solution, $x = 0$. If $y$ is a residue, then there exists a solution to $x^2 \equiv y \text{ mod } p$, which means that $-x$ is also a solution, hence there must be two. If $y$ is a non-residue, then by definition, there exists no solutions.

\medskip
Let $N_c$ be the number of solutions to $a^2 = c - b^2$. If we sum the number of ways to select $a$ for every possible $b$, we find that
$$N_c = \sum_{x \in \mathbb{F}_p} (1 + \chi(x)) \cdot (1 + \chi(c - x)).$$
This comes from fixing a dummy variable $x$, then counting the number of $a,b$ simultaneously satisfying $x = a^2$ and $b^2 = c - x$.

\medskip
This summation can be expanded to obtain
$$N_c = \sum_{x \in \mathbb{F}_p} 1 + \sum_{x \in \mathbb{F}_p} \chi(x) + \sum_{x \in \mathbb{F}_p} \chi(c-x) + \sum_{x \in \mathbb{F}_p} \chi(x(x-c)).$$
Immediately, we note that the first summation is equal to $p$. We also notice that the number of residues is equal to the number of non-residues, so the second and third summation are both $0$. From this, we simplify
$$N_c = p + \sum_{x \in \mathbb{F}_p} \chi(x(x-c)).$$
Since $\chi(x(c-x)) = 0$ when $x = 0$, we need only to sum over the non-zero values. If $x,c \neq 0$, by the multiplicatively of the character, we can factor $\chi(x(c-x))$ as
$$\chi(x(c-x)) = \chi(x^2(cx^{-1} - 1)) = \chi(x^2) \cdot \chi(cx^{-1}-1).$$
Now, notice that since $x$ iterates over all elements of $\mathbb{F}_p^*$, so does $x^{-1}$. Additionally, multiplication by $c$ simply permutes the elements, so $cx^{-1}$ iterates over all $\mathbb{F}_p^*$. Hence, $cx^{-1}-1$ iterates over $\mathbb{F}_p \backslash \{-1\}$. Summing $\chi(y)$ over all non-zero $y$ gives us $0$, but this sum is over the whole space \textbf{except} $-1$, the sum evaluates to $0 - \chi(-1) = - \chi(-1)$.

\medskip
By Euler's criterion,
$$\chi(a) = a^{\frac{p-1}{2}} \text{ mod } p \ \ \Rightarrow \ \ \chi(-1) = (-1)^{\frac{p-1}{2}}.$$
Overall, we have
$$N_c = p - (-1)^{\frac{p-1}{2}}.$$

If $c = 0$, then the summand is $\chi(-x^2) = \chi(-1) \cdot \chi(x^2)$. If $x = 0$, this term is $0$, while if $x$ is non-zero, then $\chi(x^2) = 1$ as it is guaranteed a residue. 
% Hence, the sum evaluates to $(p - 1) \cdot \chi(-1)$. 
Applying Euler's criterion once more, the number of solutions for $c = 0$ is
$$N_0 = p + (p-1)(-1)^{\frac{p-1}{2}}.$$
So, we have the number of solutions for an arbitrary $c$ is given by
$$N_c = \begin{cases}
    p + (p-1)(-1)^{\frac{p-1}{2}} & c = 0, \\
    p - (-1)^{\frac{p-1}{2}} & c \neq 0.
\end{cases}$$

\medskip
Since the number of solutions to $a^2 + b^2 \equiv c \text{ mod } p$ when $c \neq 0$ is bounded by $p+1$, the probability of randomly selecting $a,b$ and generating a specific $c$ is bounded by
$$\frac{p+1}{p^2} \approx \frac{1}{p},$$
so this process appears uniform. If $c = 0$, we expect slightly more bias: $N_0$ is bounded by $2p-1$, thus
$$\frac{2p-1}{p^2} \approx \frac{2}{p},$$
however in both cases this bias is negligible for large $p$.

\medskip
When $p = 2^{255}-19$, the prime that we are interested in, we have that $N_0 = 2p-1$ and $N_c = p - 1$ for non-zero $c$, which yields the same conclusion as above: the bias introduced here is negligible. Therefore, we conclude that summing two Elligator outputs is sufficient to remove any bias.


\subsubsection{Implementation Observations}
\begin{enumerate}
    \item The cofactor clearing happens separately before addition. In RFC 9380 Section 3, it is specified that this clearing happens after summation. While the result is mathematically equivalent, it should be noted that it does not exactly match the spec.
    \item There is no domain-separating tag used when \verb+BLAKE2b+ is called, which is required by RFC 9380.  The simple-API call \verb+blake2b(out, 64, preimage, len, NULL, 0)+ leaves BLAKE2b's \verb+personal+ and \verb+salt+ parameters at their default zero, and the single in-tree call site (\verb+derive_key_image_generator+) prepends no DST string to the preimage. \subsection{Mathematical Overview}
The leaf consumed by the FCMP++ Merkle tree is the triple $(O, I, C)$, where $O$ is the output public key, $I$ is the key-image generator associated with $O$, and $C$ is the Pedersen commitment to the amount.  The functions in this section take a structurally heterogeneous \verb+OutputPair+ (Legacy or Carrot; see \S 10 for the dispatch surface) and assemble the canonical $96$-byte $(O,I,C)$ tuple on the prime-order subgroup of ED25519: torsion is cleared on Legacy inputs (using \verb+get_valid_torsion_cleared_point+ from \S 6); identity points are explicitly rejected so that a single $1 - y = 0$ cannot zero every batched inversion downstream (the \verb+fe_invert(0) = 0+ Fermat artifact discussed in \S 4); and $I$ is derived from the original $O$ rather than from its torsion-cleared counterpart, in order to preserve the $1$-to-$1$ correspondence between key images and historical outputs.

\subsubsection{Implementation Observations}
\begin{enumerate}
    \item \verb+output_to_leaves+ is the public composition of \verb+output_to_tuple+ and \\\verb+output_tuple_to_pre_leaf_tuple+, followed by batch inversion (\verb+fe_batch_invert+), Weierstrass conversion (\verb+fe_ed_derivatives_to_wei_x_y+), and FFI marshalling \\ (\verb+selene_scalar_from_bytes+).  The output is a flattened vector of $6$ \verb+SeleneScalar+s per output (three points $\times$ two Weierstrass coordinates).
    \item Per-output exceptions thrown during torsion clearing or identity rejection are caught by the threadpool lambda and the corresponding output is recorded as invalid, preserving forward progress on the rest of the batch.
    \item Identity rejection inside \verb+point_to_ed_derivatives+ is important for correctness since a $1 - y = 0$ entry would propagate through Montgomery's trick in \verb+fe_batch_invert+ and zero out \emph{every} inversion in the batch, not just the offending one.
\end{enumerate}

\subsubsection[Conclusion]{Conclusion \hfill \checkmark}
The pipeline correctly composes torsion clearing, identity rejection, batch inversion, Weierstrass conversion, and FFI scalar marshalling, with per-output exception isolation that prevents a single malformed output from corrupting the rest of the batch. In our opinion, the implementation is fit for use.
